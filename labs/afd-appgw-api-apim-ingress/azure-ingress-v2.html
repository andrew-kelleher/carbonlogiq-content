    Architecture and policy notes
    • Global and regional ingress. Front Door Premium is the public endpoint. It uses an approved Private Link connection to an Application Gateway v2 frontend in UK South. Application Gateway forwards /api/* to the private API Management gateway. A separately configured regional WAF can make its own decision. Match the HTTPS origin hostname and certificate to the Application Gateway listener, and configure private DNS, backend TLS and health probes for the API Management gateway.
    • Edge inspection. The modeled policy checks the custom Block at priority 10 and custom Allow at priority 20, before the managed Default Rule Set. In Prevention mode a matching Allow ends evaluation of the remaining custom and Default Rule Set rules. The separate HTTP DDoS ruleset, when enabled, runs before custom rules. The simulated DRS 2.0+ policy uses an anomaly threshold of 5 and a Block action. In Detection mode the request is forwarded and Azure can log matches when diagnostics are enabled. The trace shows modeled matches.
    • API access. The example uses validate-azure-ad-token with its default 401 on failure, then a separate role condition using return-response for 403. rate-limit-by-key uses a verified client identity and returns 429 when its counter is over limit. The demo skips the counter when token validation is disabled and rejects requests if a role is required without a verified identity.
    • Private backend. The Kubernetes Service exposes an internal Azure load balancer and forwards to an orders pod. The topology assumes private network reachability from API Management to that Service. Authenticate the API Management-to-backend hop as appropriate.
    • Find the source of a 403. For an edge decision, look up the response's X-Azure-Ref in Front Door WAF logs with diagnostics enabled. For an API decision, use an authorized API Management request trace to inspect the inbound role check.
